# BLUX cA Dataset

Construction and repair records for BLUX cA 2. Each record pairs a plain-language engineering task with a small synthetic repository snapshot and the exact steps given to the pinned cA engine (and, for validation-aware work, DAT), and stores what the engines actually produced: minimal ca.changesets with exact diffs, refusals with stable error codes, DAT reports, rollbacks, recoveries and the final file tree. cA never certifies its own work, and every result says so; only DAT's reports judge the result.

Version **2.0.0** (2026-10-25), 132 records, records digest `b894a01a6e00688b…`.

## Splits

| split | records | use |
|---|---|---|
| `train` | 51 | training |
| `validation` | 20 | model selection during training |
| `test` | 30 | evaluation; never trained on |
| `holdout` | 14 | final, rarely-run evaluation; never trained on |
| `adversarial` | 9 | robustness: hostile, conflicting or malformed input; never trained on |
| `regression` | 8 | exact engine-behaviour pins that detect drift; never trained on |

- **Locked.** Each record's split is fixed in `splits.lock.json`, and a locked id never changes split or content. A change needs a new variant id; the old one is retired, never reused.
- **Grouped by family.** All variants of a seed family share one split, so near-identical records cannot sit on both sides of a split boundary.
- **Protected.** test, holdout, adversarial, regression are protected. The only training export (`python -m dstool export --purpose training`) reads train and validation only and refuses any record that is protected, locked to a protected split, or carries the canary.

## Record format

Each line of `data/<split>.jsonl` is one `blux.dataset-record` v1 (`schemas/record.v1.schema.json`):

```text
record_id   <prefix>:<family>:<variant>, immutable
category    one of the categories above
split       one of the six splits
task        {instruction}: the request in plain language
input       what the engine was given
expected    what the pinned engine actually produced (an artifact, a result, or an error)
provenance  origin, authors, licence, seed file + hash, generator, engines (with commits), review
quality     score, threshold and components
hashes      input, expected and content SHA-256
canary      the dataset canary on protected records, else null
```

For this dataset, `input` is `{workspace: {files, executable?}, steps: [...]}`: a synthetic repository snapshot and the steps run against it (cA capability calls, DAT audits, rollback, interruption and recovery; dstool/adapters/ca.py documents them). `expected` is `{steps: [{kind, output}], final_tree: [{path, mode, sha256}]}`: every step's real output (a `ca.result` with its changeset, a cA error, a `dat.report`, a rollback or recovery) and the resulting files. Every `ca.result` validates against cA's own schema and has `certified: false`.

## Contamination controls

- **Exact duplicates.** Records with the same normalized text (lower-cased, numbers folded) are dropped within a split and are a build failure across splits.
- **Near duplicates.** A Jaccard similarity of 4-token shingles of at least 0.8 between records of different splits fails the build. `data/contamination.json` lists each protected record's nearest record in another split.
- **Families.** A family spanning two splits fails the build.
- **Canary.** Every protected record carries the canary string `4e13317e-3a46-42e3-95cf-c7b29f4eee76`. If it appears in a training corpus, that corpus contains this dataset's protected records.

## Quality

- **Gates.** Every record is schema-valid and reproducible (two engine runs agree), and passes the privacy and hidden-reasoning scans.
- **Score.** The score is the mean of these components: instruction length, grounding (the instruction names something in the input), evidence where applicable, informative output, and distinctness from other families in its split.
- **Threshold.** Records below 0.6 are excluded and listed in `data/manifest.json`.

## Reproducing and validating

How the dataset is built and checked is documented in `docs/ENGINEERING.md`.

```bash
pip install -r requirements.txt            # the pinned engines and jsonschema
python -m dstool build --check             # regenerate everything; byte-identical or exit 1
python -m dstool validate                  # records, hashes, lock, contamination, manifest
python -m dstool export --purpose training -o train.jsonl
python -m pytest
```

## Intended use

- Training and evaluating models to turn engineering instructions into minimal, exact, reviewable changesets rather than whole-file rewrites.
- Teaching validation-aware repair: an independent validator (DAT) judges the work, repairs are bounded, refusals are correct answers.
- Regression testing cA: the `regression` split pins exact engine outputs; the `adversarial` split pins refusals.

## Out of scope

- Treating cA's output as validated: cA never certifies its own work; only the DAT reports in a record judge it.
- Training on test, holdout, adversarial or regression records.
- Real-world repositories: snapshots are small and synthetic.

## Limitations

- Workspaces are small, text-only synthetic snapshots; binary files and symlinks are not represented.
- Expected outputs are what cA 2.0.1 and DAT 4.0.0 produce, not human-reviewed ideal patches.
- Instructions are English only.
- Variants within a family share structure, so the effective diversity is the number of families, not records.
